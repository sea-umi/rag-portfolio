# Phase 2 提案書

## 1. 提案の前提

現在はCloudflare Pages静的UI、Worker、D1、Vectorize、Gemini、ローカルPython取り込みで構成しています。教材用の5文書・12問を対象とした、ポートフォリオ用MVPです。Cloudflareの国内リージョン保証はありません。

本提案は、MVPで価値と課題を確認した後に、必要な機能を段階追加するための案です。実案件では文書数、利用者数、権限、個人情報、データ所在地、費用を確認して詳細設計します。

## 2. MVPでできること／できないこと

### できること

- 匿名でask（質問）とsearch（検索）を利用できる。
- ローカルPythonから文書を取り込み、分割・Embedding・登録できる。
- ingest（取り込み）だけは `X-Ingest-Token` で簡易保護する。
- 教材データでRAGの基本的な流れを確認できる。

### できないこと・注意点

- 認証は未実装で、ask/searchは匿名利用である。
- 部門別権限、RLS、ユーザーごとの検索制御は未実装である。
- searchは本文を返すため、公開範囲を慎重に管理する必要がある。
- `X-Ingest-Token` は取り込み用の簡易トークンで、利用者認証や部門別認可の代わりにはならない。
- 旧Supabase/FastAPI経路が残っており、移行・廃止方針が必要である。
- 本格的な監査ログ、精度評価、利用量監視、アラートは未実装である。

## 3. Phase 2の提案

### 3.1 認証・認可

Cloudflare AccessまたはWorker側の認証を導入し、社内メールやSSOで利用者を確認します。所属部門と文書メタデータを照合し、D1とVectorizeの検索に部門フィルタを適用します。操作・質問・検索の監査ログも記録します。

認証方式（Cloudflare Access、OIDC、SSO連携、Worker実装）の選択で工数が変わるため、方式決定後に再見積します。SSOの要件、部門情報連携、権限同期、既存利用者・データの移行、監査対応の範囲は別途確認します。

受け入れ条件・KPIは、認証なしアクセスを拒否すること、権限外文書の返却0件、主要操作の監査ログ記録率100%です。暫定KPIとして、出典付与率95%以上、P95応答時間5秒以内、取り込み失敗通知15分以内、権限外文書返却0件、監査対象操作記録率100%を置き、実データで正式値を再設定します。

### 3.2 Word／Confluence／Excelなどの取り込み

各サービスのAPIやファイルを読むコネクタを用意し、本文・表・見出しを共通形式へ変換します。元システムの文書ID、更新日時、所有部門、閲覧権限をメタデータとして保持し、権限を検索時にも引き継ぎます。権限を取得できない文書は取り込みを保留します。

受け入れ条件・KPIは、指定文書を再現性高く取り込めること、文書IDと出典を追跡できること、権限欠落文書を誤公開しないことです。

### 3.3 差分更新

現状の `content_hash` は、取り込み処理内で同一チャンクのupsert・重複登録を防ぐための識別に使います。これはチャンク単位の重複防止であり、文書が更新・削除されたことを管理する仕組みとは別です。

Phase 2では文書単位の同期情報（元システムの文書ID、`content_hash`、更新日時、削除状態、権限メタデータ）を管理します。更新時は旧チャンクを削除または無効化してから変更後の文書を再分割し、変更分だけを再Embeddingします。削除された文書は検索対象から除外し、必要に応じてVectorizeから旧チャンクを削除します。更新日時を比較して変更のない文書は処理対象外にします。

受け入れ条件・KPIは、同一内容で不要なEmbeddingをしないこと、変更・削除が検索結果に反映されること、全件処理より再Embedding件数と時間を削減できることです。削減率は実データ計測後に決めます。

### 3.4 Slack連携

Slack Botで質問を受け、利用者の権限を確認したうえで、出典付き回答を返します。Bot権限は最小限とし、レート制限、タイムアウト、失敗時の案内を設けます。

受け入れ条件・KPIは、権限外情報を返さないこと、回答に出典を付けること、応答時間（P95）とエラー率を計測することです。

### 3.5 管理画面

文書一覧、取り込み状況、失敗内容、質問ログ、精度評価、再取り込みを管理者が確認できる画面を追加します。再実行や削除には権限確認と確認操作を設けます。ログの保存期間と閲覧範囲も決めます。

受け入れ条件・KPIは、失敗原因の確認と再取り込みができること、質問・回答の評価を記録できること、管理操作が監査ログに残ることです。

### 3.6 運用監視

Worker、D1、Vectorize、Geminiのエラー、レイテンシ、利用量を記録します。取り込み失敗、回答失敗、利用量急増、レイテンシ悪化を検知してアラートを送ります。GeminiとCloudflareの利用量・費用も確認します。

受け入れ条件・KPIは、主要エラーを検知・通知できること、エラー率・レイテンシ・利用量を集計できること、未処理エラーを残さない運用ができることです。

## 4. 推奨ロードマップと優先順位

原則として、次の順番を推奨します。

| フェーズ | 内容 | 期間（要件確定後の参考） | 主な成果物 | 主な依存関係 |
|---|---|---:|---|---|
| Phase 2-A | 認証・権限 | 4〜8人日 | 認証方式、権限モデル、アクセス制御、監査設計 | 要件、SSO・部門情報の確認 |
| Phase 2-B | 文書単位の差分更新 | 4〜7人日 | 同期管理、旧チャンク削除、削除除外、変更分のみ再Embedding | 文書ID・更新日時・権限メタデータ |
| Phase 2-C | 管理・監視 | 5〜10人日 | 管理画面、失敗通知、ログ・メトリクス、再実行手順 | 2-Aの権限、2-Bの同期状態 |
| Phase 2-D | 追加コネクタ | 3〜8人日／コネクタ | 共通変換、取り込み設定、出典・権限メタデータ | 2-A、2-B、対象API仕様 |
| Phase 2-E | Slack | 3〜6人日 | Slack Bot、権限確認、出典付き回答、運用手順 | 2-A〜2-D、Slack権限・イベント要件 |

期間は「要件確定後の参考」であり、対象件数、既存API、認証方式、テスト・移行・監査対応の範囲で再見積します。MVPから本番利用へ移行する判断基準は、認証・権限が有効で権限外文書返却0件を確認できること、差分更新と削除反映を検証できること、暫定KPIを実データで計測できること、監視・失敗通知・監査ログ・復旧手順が運用できること、費用とデータ保護・保存期間・責任範囲が承認されることです。

実装順は次のとおりです。

1. Phase 2-A 認証・権限
2. Phase 2-B 差分更新
3. Phase 2-C 管理・監視
4. Phase 2-D 追加コネクタ
5. Phase 2-E Slack

認証・権限を先に行うのは、追加コネクタやSlackを先に作ると、後から権限設計を作り直す可能性が高いためです。差分更新は、文書数が増えたときの処理時間とEmbedding費用を抑えます。その後、管理画面と監視で失敗・費用・精度を確認できるようにします。共通形式と権限メタデータが固まってからコネクタを増やし、認証・出典表示が整ってからSlackを追加します。

## 6. セキュリティ・個人情報・データ所在地・コスト

- ログインできても、文書を見られるとは限らない設計にする。
- 文書、質問、回答、Slackメッセージの個人情報・秘密情報について、保存期間、マスキング、削除方法、閲覧権限を決める。
- 出典やログに、不要な本文を過剰に残さない。秘密情報や実文書の内容を提案書に書かない。
- 公開URLやリソース識別子は秘密値ではないが、公開範囲やアクセスログから推測される情報を意識して管理する。秘密値（トークン、鍵、パスワード等）はURLや提案書に含めない。
- Cloudflare、Gemini、連携先のデータ処理場所・保存・学習利用条件を確認する。国内リージョンが必要な実案件では、構成を再選定する。
- Gemini、Embedding、Vectorize、D1、ログ、Slackの利用量を見積もり、予算上限とアラートを設定する。
- 旧Supabase/FastAPI経路の残置期間、データ同期、責任範囲、廃止条件を決める。

## 7. クライアントへの説明

「Phase 2はやらない」という意味ではありません。まずMVPでRAGの基本価値と課題を確認し、その後に認証・権限、差分更新、管理・監視、追加コネクタ、Slackを段階的に追加します。MVPには認証・部門別権限・本格監視がないため、機密文書を扱う本番環境へそのまま使うのではなく、安全性・費用・使いやすさを確認しながら拡張します。
