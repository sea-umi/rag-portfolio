# 案件3 社内文書検索AI（RAG）制作手順と学習メモ

> この文書は、学習・制作の流れと、制作中に確認した疑問を初心者向けに整理したものです。秘密値、APIキー、トークン、実文書の内容は掲載していません。

## 第1部　制作手順

### 1. 課題理解

社内文書を質問で検索できるRAGを作る課題として整理した。最初に、文書量と更新頻度、利用者、アクセス範囲、予算、必要な回答精度を確認する。これらが決まらないまま技術を選ぶと、必要以上に大きな構成になったり、権限や運用が不足したりするためである。

### 2. 提案とMVP

MVPとは、最小限の機能で価値を確かめる最初の版である。今回はPDF 5件を教材に、質問、関連箇所の検索、回答、ページ付きの出典表示までをMVPとした。部門別権限や差分更新などはPhase 2へ分離し、まず動作と精度を確認する。回答の根拠を表示し、文書に根拠がない場合は「不明」と返すことで、ハルシネーション（根拠のないもっともらしい生成）を抑える。

### 3. Worktreeでの並行開発

Git worktreeとは、同じGitリポジトリを複数の作業フォルダとして扱う仕組みである。`rag-ingest`（取り込み）、`rag-search`（検索API）、`rag-ui`（画面）を並行開発でき、ブランチを頻繁に切り替えずに済んだ。最後に成果物をポートフォリオ用の1リポジトリへ整理した。複数フォルダは別々のリポジトリではなく、同じ履歴を共有する作業場所だと理解した。

### 4. RAGの実装

処理の流れは次のとおりである。

1. PDFから本文を抽出し、ページ番号を保持する。
2. 本文を検索しやすい長さにチャンキング（分割）する。
3. Gemini Embeddingで各チャンクを768次元のベクトルに変換する。
4. Cloudflare Workerを経由して、本文をD1、ベクトルをVectorizeへ保存する。
5. 質問もEmbeddingし、Vectorizeで近いチャンクを検索する。
6. 検索結果を使ってD1から本文を取得し、Geminiで回答を生成する。
7. 回答とともに文書名・ページ番号などの出典を表示する。

### 5. ローカル取り込みと公開UI

ローカルのPython取り込み処理は、PDFを読み、Embeddingを作り、Workerの取り込みエンドポイントへ送る役割を持つ。公開UIは利用者の質問をWorkerへ送り、WorkerがVectorize検索、D1本文取得、Gemini回答生成を行う。つまり、ローカル取り込みは初期登録・更新の入口であり、公開UIの質問処理とは別の経路である。

### 6. Geminiを両方に使った理由

Embeddingは文章を数値のベクトルにする処理、回答生成は検索結果を自然な文章にする処理である。今回は同じGemini系サービスを両方に使い、API管理、学習、設定を一つにまとめた。MVPでは構成を理解しやすく、別サービスを組み合わせる運用負担も小さいためである。

### 7. Supabase案からCloudflare構成へ

当初はSupabase案も検討したが、今回の公開先と実装方針に合わせて、Cloudflare D1（本文データベース）、Vectorize（ベクトル検索）、Pages（UI公開）、Worker（API処理）へ切り替えた。サービス間の役割が明確で、PagesとWorkerを同じCloudflare側で扱いやすいためである。国内リージョン要件は本ポートフォリオでは適用外とし、実案件ではデータ所在地・契約・法務要件を先に確認する。

### 8. 公開時の設定と注意

WranglerはCloudflareを操作するCLIツールである。認証後、SecretsへAPIキーや取り込み用トークンを登録し、コードやGitHubへ直書きしない。CORSはブラウザからAPIへアクセスできる送信元を制御する仕組みで、公開時は許可先を必要最小限にする。公開エンドポイント、認証、ログ、レート制限、費用、個人情報の扱いも確認する。

### 9. テストと公開

12問をテストし、教材から回答可能な10問と、文書に根拠がなく不明とすべき2問を確認した。APIだけでなくUI上でも、回答内容、出典、エラー時の表示を確認した。その後、GitHubへ公開し、Cloudflare PagesでUIを公開する。README、運用手順、アーキテクチャ、Phase 2提案を整備し、第三者が構成と再現手順を理解できる状態にする。

## 第2部　気になって確認したこと（初心者向けQ&A）

### RAGとは何か

RAG（検索拡張生成）とは、AIが回答する前に登録文書を検索し、その結果を根拠に回答する方式である。今回の例では、質問に近いPDFのチャンクを検索してGeminiに渡し、出典ページとともに回答する。

### PDFを分解してベクトル化する意味は？文書追加時は？

PDF全体を一つの文章として扱わず、意味のまとまりに分けてベクトル化すると、質問に関係する部分だけを検索できる。新しい文書を追加した場合は、原則として抽出・分割・Embedding・保存を再処理する。既存文書を変えない差分更新なら、新規・変更部分だけを処理する設計にできる。

### チャンキング、Embedding、Vectorize、pgvectorとは？

チャンキングは長文を検索単位に分けること、Embeddingは文章を意味を表す数値列に変換すること、Vectorizeはその数値列を高速検索するCloudflareのサービスである。pgvectorはPostgreSQLにベクトル検索機能を追加する拡張で、Vectorizeは専用サービス、pgvectorはPostgreSQL内で扱う方式という違いがある。

### 分割サイズはどう考える？

「文書総文字数÷700〜800」は、初期のチャンク数を見積もる目安であり、厳密な正解ではない。細かすぎると文脈が切れて検索結果が断片的になり、大きすぎると無関係な内容が混ざり、回答に渡す量や費用も増える。見出し、段落、ページ境界も考慮してテストする。

### 文書量が増えたらDBを変えるべき？

文書量、検索速度、更新頻度、権限、費用、バックアップ要件で選ぶ。課題はPDF 5件のMVPなので、最初から大規模構成にせず、D1とVectorizeで流れを完成させる判断をした。利用が増えた段階で専用DBやキュー、監視を検討する。

### EmbeddingにもAPIが必要？Geminiを両方に使う理由は？

必要である。Embeddingも外部モデルを呼び出す処理なのでAPI利用が発生する。今回は回答生成とEmbeddingをGeminiに統一し、設定と学習対象を減らした。

### 3072次元と768次元、設定不一致、Worktreeの課題は？

次元数はベクトルの要素数で、3072は768より表現容量が大きい一方、保存量や計算量も増える。Embeddingモデル、Vectorizeのindex、検索側の設定は同じ次元数でなければならない。別プロジェクトや別経路で3072と768が混在すると登録・検索に失敗する。Worktreeでは環境変数、モデル名、設定ファイルが作業場所ごとにずれやすいため、共通の設定表と`.env.example`を用意して確認する。

### Supabaseの無料枠、移行、招待は？

無料枠は個人学習の検証には便利だが、容量・停止条件・利用規約を確認する。プロジェクト移行はデータ、環境変数、認証、URLを別々に確認する作業であり、単純なフォルダ移動ではない。招待は必要な権限だけを付与し、共有トークンを回覧しない。

### Cloudflare D1の無料枠はプロジェクト単位？企業利用は？

無料枠や上限はサービス・アカウント契約の条件で決まるため、プロジェクトごとと決めつけず、最新の料金表とダッシュボードを確認する。企業利用では、アカウント全体の利用量、複数環境の合算、請求、監査、データ所在地、バックアップ、権限を確認する。

### ローカルPythonはD1・Vectorize・Worker・UIにどう作用する？

PythonはPDFを処理してWorkerへ送る。WorkerがD1とVectorizeへ書き込み、UIはWorkerの検索APIを呼び出す。ローカル処理を実行しただけでUIが直接DBを読むわけではなく、公開時もUI→Worker→D1/Vectorizeという境界を保つ。

### Cloudflareアカウント、サインイン、workers.dev、Pagesとは？

Cloudflareアカウントは各サービスを管理する入口で、WranglerのサインインはそのアカウントとCLIを結び付ける操作である。`workers.dev`はWorkerを試しに公開できるドメイン、PagesはWeb UIを公開するサービスで、最終的な公開URLは設定したプロジェクト名などから決まる。URLは公開情報でも、管理画面や秘密値は公開しない。

### Wranglerとは？CLIから作成するとは？

WranglerはAPI、言語、ライブラリではなく、Cloudflareのリソースを端末から作成・設定・公開するCLIツールである。コマンドでWorkerを作り、設定やSecretsを登録し、デプロイすることを「CLIから作成・公開する」と表現する。

### HTTPとHTTPSをどう例える？

HTTPは手紙をそのまま運ぶような通信、HTTPSは封筒に鍵をかけて運ぶような通信である。HTTPSでは通信内容の盗み見や改ざんを防ぎやすい。公開UI、API、ログイン情報はHTTPSを使う。

### APIキーをターミナルへ貼ってよい？Secretsとは？

APIキーをコマンド履歴、画面共有、ログ、Gitに残すのは危険である。CloudflareのSecretsへ登録し、Workerの実行時だけ参照する。`INGEST_TOKEN`は、文書取り込みエンドポイントを誰でも実行できないようにする共有認証値であるが、運用では定期更新、漏えい時の失効、より強い認証を検討する。

### 3000番ポート、Node.js、複数プロセス、ローカルと公開環境

ポートは建物の受付番号のようなもので、`3000`番はローカルUIが待ち受ける番号の一例である。Node.jsはJavaScriptをサーバーなどで実行する環境である。UI、Workerのローカル版、取り込み処理などを同時に動かすと複数プロセスになり、それぞれ別ポートや別端末が必要になる。ローカルは自分のPC内、公開環境はインターネット上のCloudflareで、環境変数・URL・認証・費用が異なる。

### GitHubとCloudflare Pagesの関係は？何を除外する？

GitHubはコードを保管・共有する場所、Cloudflare PagesはそのコードからUIをビルドして公開する場所である。GitHub連携なら更新を検知して公開できる。`.env`、APIキー、PDF、生成物、`node_modules`などは、秘密漏えい・著作権・容量・再現性の問題があるためGit管理から除外する。

### 出典表示と「不明」が重要なのはなぜ？

出典表示は、回答がどの文書・ページを根拠にしたかを利用者が確認できるようにする仕組みである。文書にない質問へ無理に答えると誤情報になるため、検索結果が不十分なら「不明」と返すことが信頼性と安全性につながる。
